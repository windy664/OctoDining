# 好好吃饭：先回答下一餐吃什么

面向需要在有限生活费内安排食堂餐食的学生。首页直接展示**下一餐**：已有确认计划就显示原计划；没有计划就从当前食堂菜单给出一道可确认的建议。用户可以换菜、查看候选、记录实付金额；一周餐表是副页，Agent 输入是调整入口，不是打开应用的门槛。

## 首次使用

输入每月可支配生活费、非餐饮固定开销和缓冲金。应用按 `(生活费－固定开销－缓冲金) / 30` 估算每日餐饮预算；30 天只是可解释的起始假设。默认可使用随包附带的广州软件学院菜单快照；也可粘贴含来源、更新日期、时区、商品名、店铺、类别、价格和营业时段的 JSON，应用校验后存入本地。`scripts/menu-csv-to-json.py` 可将指定 CSV 转成可粘贴的 JSON。目前宿主没有应用可用的文件选择接口，因此还不能在界面里直接选择 CSV，也没有自动采集。

预算分配会限制每日总额及各餐候选，但不把价格低等同于吃得好。午晚餐排除明显的加料、纯主食和小份条目；早餐有单独候选池。商品名称无法证明份量、营养、过敏原或实际库存，用户仍需核对。

## 一周餐表

应用从当前日期生成七天草案，跳过今天已过的餐次，保留已确认计划，按预算、餐次、营业时段与历史重复情况选菜。草案展示缺口与逐日金额；用户点击确认后，整周写入本地并读回。可以逐餐调整、取消，或记录实际花费与撤销。草案由本地规则生成，**不是 Agent 自动编排**；已确认餐表也不是订单。菜单太少、条件不满足或预算不足时，应保留缺口而不是编造菜品。

## Agent 的职责和边界

在单餐候选页面，用户可以请求 OctoSense 宿主的 `octos.turn.start` 比较至多三个真实候选。应用验证候选序号与上下文，用户再确认保存。无模型或拒绝授权时仍可人工选菜。真实模型闭环的同版证据目前属于 1.2.2；1.7.0 的本地功能与 card-host 已验证，Shell / 模型仍需同版复验，详见[参赛准备状态](CONTEST_READINESS.md)。

自动抓取外部菜单、实时售价与库存、营养或过敏安全判定、下单和支付不在当前功能范围。
