# 好好吃饭：先分配饭钱，再回答今天吃什么

产品要替用户减少每天选餐的负担，同时让他看得见预算和依据。首页不是餐厅搜索页，也不是聊天首页。

## 用户状态与主界面

| 状态 | 第一屏应显示 | 下一步 |
| --- | --- | --- |
| 首次使用、尚无资料 | 食堂数据来源、生活费分配引导 | 算出每日餐饮预算，说明可用数据边界 |
| 已有餐表且今天有安排 | 今日已确认的餐品、金额、店铺和到店时间 | 查看餐表、修改或取消 |
| 已完成设置，但今天未安排 | 一道与预算、餐次和时段相符的推荐菜 | 确认、换一道，或告诉 Agent 新需求 |
| 无可核验的菜单或预算不足 | 缺口和可调整项 | 导入/修正数据、改预算；不编造餐品 |

一周餐表是副页，显示已确认与待安排的日期。输入框用于调整建议，不要求用户先发消息才知道吃什么。

## 新人引导与预算

用户输入**每月可支配生活费**、本月非餐饮固定开销、缓冲金。应用用 `(生活费－固定开销－缓冲金) / 30` 估算日餐饮预算，再以早餐 22%、午餐 39%、晚餐约 39% 给出起始上限。30 天和比例是可改的产品假设，不是营养标准或财务建议；用户仍可改日预算、单餐上限和餐次。预算偏紧时应清楚提示，不能为了填满三餐而推荐加料、纯主食或没有完整餐线索的商品。

1.5.0 已接入内置广州软件学院食堂快照和上述预算核算，并保存设置。**外部菜单文件导入还没有实现**；新用户不在该食堂时，当前不能声称有真实可用的推荐。下一步应优先做用户自带 CSV/JSON 的导入、字段映射、去重、价格与营业时段校验、来源和更新日期显示。自动采集放在导入后评估，需要站点许可、更新频率与失败处理，不能静默抓取并把旧价当现价。

## “不亏待自己”的算法边界

菜单仅有名称、类别、店铺、价格和营业时段，没有份量、营养、过敏原或实售状态。“最佳餐表”不能被严格证明。可验证的第一层是：每天不超预算；午晚餐优先明显带主食及蛋、肉等主菜线索的条目；避开加料、配菜、纯主食、饮料和明显小份；安排营业时段；一周尽量减少同菜、同店连续重复。对是否吃得饱、营养均衡、过敏安全，必须让用户核对，不能让 LLM 猜。

现有规则只完成单餐推荐和部分历史避重复；1.5.0 对午晚餐候选增加了粗筛。下一阶段应生成**一周草案**，逐日展示预算、三餐、菜单来源和无法判断的项目；用户可替换后再确认。草案不能直接冒充已确认计划。完成后再让 OctoSense Agent 在可用候选之间解释多样性和个人偏好，输出必须受应用的价格、时段、预算与商品 ID 校验；最终保存由用户确认。

## 下一阶段验收

1. 导入一份新食堂表；拒绝无效价格、重复项和无来源数据，保留原文件，不把导入失败当成功。
2. 输入生活费与必要支出，复算每日预算；固定支出改变后，旧草案标为过期，已确认餐表不被悄悄覆盖。
3. 生成七天三餐草案；逐日核算不超预算，正餐不出现加料或纯主食，找不到合适候选时留空并说明原因。
4. Agent 只在真实候选与草案内决策；用户查看、调整、确认后保存并读回，重启仍见计划。
