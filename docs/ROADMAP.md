# 当前开发路线

更新：2026-10-03。按“基本功能 → 系统 Agent → UI”推进，先完成一个能复现的餐饮任务。以下均为待办，只有取得对应证据才能标为完成。

## P0：修复应用包并验证宿主

这是下一次开发首先要做的工作。

- 同步 `scripts/main.splash.in` 与 bundle 品牌文案，确认重新生成不会丢失改动。
- 统一源码调用与 manifest 权限；按采用的助手接口申请精确的 `octos.*` 能力，移除未使用的直连模型配置。
- 在 card-host 验证筛选、候选显示、确认入口及 Agent 不可用状态。
- 准备 OctoSense Shell，依照宿主锁定的依赖构建；验证 Linux 下加载本地应用。
- 记录宿主、octos、App Hub、Makepad/OctoScript 依赖版本、构建特性和启动命令。

**通过条件：** 同一份生成应用可加载、可交互，权限与调用一致；在 OctoSense Shell 中取得运行证据。card-host 的成功不能替代这个条件。若 Linux 宿主受阻，记录具体错误、尝试范围与可复现替代方案，再决定是否采用已有 Rinx 路线，避免同时维护两套产品。

## P1：让基本功能完整

- 将 A1–A6 迁入 OctoScript；明确原来的每日预算与当前单餐输入的换算方式，用户可覆盖默认值。
- 保存计划时包含日期/餐次、候选来源和预算依据，检查写入结果并读回。
- 重新打开恢复计划；支持修改和取消，重复确认不重复计入。
- 展示已计划金额与剩余计划预算，金额运算准确；计划金额不等于实际消费。
- 输入条件变化后使旧候选失效，禁止保存与当前条件不符的结果。
- 验证无候选、缺失营业时段、非法输入、存储失败和未支持饮食要求。

**通过条件：** 以固定菜单完成“输入 → 候选 → 确认 → 保存 → 重新打开 → 修改/取消”，金额和来源全程可核对。无模型时基本功能仍可使用。七日规划在此之后迁入，保留已有网页和 Rust 算法用于对照。

## P2：结合系统 octos 完成 Agent 任务

- 在宿主配置模型提供方，开启应用助手路径并走正常授权；应用不收集密钥。
- 向 Agent 提供经过筛选的候选、用户偏好和相关计划历史。
- 对模型结果做可验证约束，防止编造菜品或接受过期建议；写操作仍由应用在用户确认后执行。
- 记录一次真实请求、建议、确认后的状态变化，以及金额和存储核验。
- 测试拒绝授权、未配置模型、超时、错误、重复请求与条件变化；失败时显示真实状态。
- 下一次推荐参考历史；无足够候选时明确说明无法保证不重复。

**通过条件：** 在选定宿主中完成真实 Agent 请求与计划结果核验；能指出哪些决策由 Agent 完成、哪些由应用执行、哪些由用户确认。没有模型回复时不得显示 Agent 成功。自动事件触发和应用工具注册仅在所选版本支持并验证后加入。

## P3：UI 与提交材料

- 基于已跑通流程完善布局、中文、六档入口、加载和错误反馈，再检查小窗口、滚动和长文字。
- 用真实功能替换 `listing.json` 的笔记模板，填写真实发布者与支持信息；平台声明依据实际测试。
- 采集同一版本的真实截图、任务日志和演示视频，重新 stamp/check。
- 完成数据来源、采集时间与授权说明，固定源码提交与宿主版本。
- 按赛事入口提交仓库与材料；App Hub 上架是单独的发布流程。

**通过条件：** 他人能按 README 复现同一任务，展示材料对应冻结代码，没有未实现功能的完成声明。
