# 运行时 Agent 任务与责任

## 目标任务

OctoDining 用菜单快照和本地规则找出符合餐次、预算、时段与关键词条件的候选。OctoSense 系统 Agent 只比较已经筛出的真实候选并解释取舍。应用核验返回候选序号仍有效；用户阅读信息后主动确认某个候选；应用再保存计划并读回验证。

Agent 不搜索整份菜单，不编造新菜名、价格、营业信息、营养或过敏原，也不替用户写入计划。

## 分工

| 责任方 | 做什么 | 验证方式 |
| --- | --- | --- |
| 应用 | 读取菜单、预算、时间与当日计划，筛选候选并核算金额 | 候选可追溯，金额可按规则复算 |
| Agent | 比较当前最多三个候选，按用户需求说明取舍 | 返回结构化的候选序号；应用检查序号与请求状态 |
| 用户 | 按宿主提示授权或拒绝；查看结果，确认具体计划变更 | 未确认时本地计划保持不变 |
| 应用 | 在确认后写入计划，读回核验并更新预算 | 重启可恢复；替换、取消不重复计入 |
| 宿主 | 管理模型 provider、密钥、权限、Agent 会话与审批 | 应用无法读取密钥；服务错误如实反馈 |

“编码 Agent 帮忙写过程序”“运行时收到模型文字”和“Agent 自动完成任务”是不同证据。当前作品的边界是**Agent 提供有约束的建议，用户决定，应用执行确定性写入**。

## 当前实现与验证边界

- 基本功能已在 App Hub `card-host` 开发预览中交互验收：A1–A6、三餐、筛选、预算、计划持久化与故障恢复。
- 应用通过 `host.request("octos.turn.start", ...)` 发送当前用户需求、筛选结果和当日已计划餐次；manifest 声明 `storage` 与精确的 `octos.turn.start` 能力。
- 返回值要求为只含候选序号和简短理由的 JSON。应用只接受本次候选范围内的序号；无效或过期结果不会成为可确认建议。
- 即使 Agent 给出有效建议，也必须由用户点击具体的“确认候选”按钮。Agent 不直接触发保存。
- `card-host` 不提供 OctoSense 宿主服务。OctoSense Shell 中已用 MiniMax-M3 实测首次授权、有效建议、用户确认、新建计划与读回；拒绝授权及未配置模型的回退另有记录。格式错误、超时和过期回调的 Shell 实测仍待补。

候选列表最多扫描菜单一次并返回三个不同店铺的符合项；它不是全局最优搜索。关键词避辣也不是食品安全或健康判断。

## 数据和权限

发送给宿主 Agent 的范围为：本餐次、日预算、本餐上限、到店时间、用户输入、最多三个候选的菜单字段及同日已确认计划摘要。宿主会按其配置把请求交给模型提供方。应用包不包含 API 密钥，也没有菜单服务网络权限。

## 失败与接管

- 没有候选时不请求 Agent，也不造候选。
- 宿主拒绝、未配置服务或调用失败时，显示具体非敏感错误；用户仍可手动查看候选。
- 非 JSON、越界序号及过期响应不标成有效推荐。
- 用户改变条件后立即清除旧候选和建议；已保存计划不变。
- 保存失败时不显示成功，上一条已核验记录仍可读取。
- 菜单快照没有实时库存、现价、营养或过敏原事实。
