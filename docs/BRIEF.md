# OctoDining 产品任务

更新：2026-10-04。实现进度以 [参赛准备状态](CONTEST_READINESS.md) 为准。

## 用户与目标

面向预算有限、每天反复决定吃什么的打工人和学生。用户需要在可负担的范围内吃得多样，清楚知道选了什么、计划花多少钱，并能调整自己的决定。

产品承诺是“让预算有限的人，也能好好吃饭”。A1–A6 是已有餐饮预算分档，用户可以手动改预算；它不用于判断真实资产或给人评级。当前数据覆盖广州软件学院食堂，服务范围与数据覆盖范围要分别说明。

## 第一项完整任务

以“今晚预算 20 元、18:30 到店、别太辣”为例：

1. 应用读取预算、时间、可支持的偏好，以及已确认的计划。
2. 从菜单快照筛出候选，展示名称、店铺、价格、营业时段与来源限制。
3. 接通 Agent 后，由它比较候选并解释建议；条件校验和金额计算由应用执行。
4. 用户确认一个候选，应用保存计划，再读回核验。
5. 重新打开可看到已确认计划；修改或取消时重新计算计划预算。
6. 下一次规划能参考历史，减少重复；预算或到店时间变化后需重新核验旧建议。

当前原生应用已支持三餐的候选、确认、保存与读回；首页根据菜单与已存计划给出规则推荐，用户可在其下输入需求，请宿主管理的 Agent 比较候选。七日页显示已确认餐次和待安排日期。模型不可用时保留手动选择；整周自动排餐尚未实现。

## 先完成的范围

- 迁入原有 A1–A6 选择，并区分每日预算与单餐预算。
- 完成今晚选餐、确认、保存、恢复、修改和取消。
- 剩余计划预算按已确认计划计算；没有消费回执时不能称为实际支出。
- 菜单快照中的缺失信息明确显示；无候选时允许用户修改条件。
- 基本流程不依赖模型可用；模型不可用时明确显示本地规则模式。
- 七日餐表先可靠显示已确认内容，并允许从空白日期进入安排；整周自动排餐后续验证。

## 后续扩展

更多地区的菜单接入、周计划多样性、Rinx 聚餐协作与分享。采购清单、价格追踪、天气和日历需要各自的数据来源与验收，暂不纳入首条任务。

当前没有外卖平台接入、真实订单、支付、配送、营养评估或过敏原保证。

## 赛事场景与验收

拟以“购物与物流”中的餐饮消费决策作为场景关联，先交付预算约束下的选餐与计划管理。与主办方确认最终主题表述；尚未实现的订单、物流和日历能力不写进完成清单。宿主优先验证 OctoSense Shell，Rinx 为可选扩展，依据见 [架构说明](ARCHITECTURE.md)。

验收时要证明：候选来自数据、预算核算正确、用户确认才写入、写入结果可读回、状态变化可追踪、失败不显示成功。明确展示 Agent 实际参与了哪些步骤，不把普通规则筛选或编码 Agent 的开发过程算成运行时自动化。
