# 1.8.13 七日草案 Agent 换餐：OctoSense Shell 真实模型联调记录

2026-10-10。此页记录 **1.8.13 在 OctoSense Shell 中用真实 MiniMax-M3 完成“Agent 调整整周餐表”闭环**的实测结果，以及为此发现并修复的产品缺陷。模型密钥只在本机隔离环境配置，不进入仓库。

## 环境

- 宿主：OctoSense Shell 本机构建（仓库提交 `4a541777`，desktop-v0.1.0-beta.1），Linux。
- 内核：`OCTOS_APP_CORE_BIN` 指向锁定版 octos（`target/octos-kernel` release 构建）。
- 模型：`minimax-cn` / MiniMax-M3，`https://api.minimax.cn/v1`（内核 profile 写入隔离目录 `OCTOS_APP_CORE_DIR`）。
- 应用数据：隔离的 `OCTOSENSE_APP_DATA`；本地测试目录经 `hub publish` 签名（临时锚点，非正式发布），`hub verify` 通过（catalog sequence 1）。
- 隐藏窗口远程桥驱动（`MAKEPAD_HIDE_WINDOWS=1 MAKEPAD_REMOTE=8301`）。

## 通过的流程（同一 bundle、同一次运行）

1. 首次启动完成生活费核算（¥1500 − ¥540 → 每日约 ¥32）。
2. 周页生成七天草案：待确认 20 餐，缺口 0，重复 4 次；未写入任何计划文件。
3. 输入需求“这周尽量少辣，别重复同一样菜”，点击“请 Agent 提案”。**宿主首次授权流程**：consent 记录写入 `$OCTOSENSE_HOME/approvals/consent.json`（`allowed: true`）。
4. MiniMax-M3 返回围栏包裹的 JSON；应用剥围栏、校验 `changes`/`reason`、把模型使用的“日期+餐次”文本映射回选项编号、检查边界与重复。
5. 界面展示“Agent 提议：2026-10-12 午餐: 香辣大鸡排饭 → 筒骨汤牛肉丸桂林米粉”，附模型理由。
6. 用户点“应用建议到草案”：状态显示已调整 1 餐，**计划文件仍为 0 个**（草案未落盘）。
7. 用户点“确认整周草案”：显示“已确认并读回核验 19 餐”。
8. 读回 `plans-*.json`：7 天、2026-10-12 午餐为 Agent 所选“筒骨汤牛肉丸桂林米粉 ¥12.00”；全天金额仍在预算内。

## 本次联调发现并修复的产品缺陷

1. **处理器指令预算**（每次回调 200,000 条，Makepad 常量）：备选扫描原本在草案生成同一次回调里全菜单线性扫描（约 3 万次迭代），整个处理器被静默中止，草案摘要不显示。修复：扫描移入 `start_timeout` 独立回调，收敛为最多 5 个日期、每个采样 90 道。
2. **`parse_json` 对围栏文本返回空对象而非 nil**（文档警告过）：直接解析 ```json 包裹的回复得到 `{}`，校验误以为是合法对象。修复：以“解析结果含 changes 字段”为可用标准，否则逐段剥围栏重试。
3. **`ok` 是脚本保留字**：用 `let ok` 在旧引擎编译失败（界面只剩源码）。改名为 `usable`；card-host（新引擎）此前放过了它，暴露了新旧引擎差异。
4. **模型的 `meal` 是“日期+餐次”文本而非编号**：按日期、日期加餐次名两种形式映射回选项编号，并兼容字符串数字的 `option`。
5. 缺字段访问未包 `try` 会中止回调——诊断过程确认。
